
Schema 定义「什么算匹配得好」：把每帧动画编码成一个特征向量，运行时拿角色
当前状态的特征向量到库里找最近邻。**Schema 的每一项选择都直接改变搜索结果的
质量和手感。**

## 1. 设计原则（从 Step 2/3 学到的教训延续过来）

1. **每个权重都要能讲出为什么**——不接受「默认值看起来还行」。§9.6 的教训：
   没有对照实验的数字都是拍脑袋。
2. **从最小 Schema 开始**，一次只加一个通道，录对比。通道堆多了无法归因
   ——和 §10.2 的三路对照实验同一个道理。
3. **先让度量说话再让眼睛说话**：debug 视图里的 cost 分解是客观数据，
   「感觉响应快了」是需要被数据支撑的主观印象。

## 2. 通道设计

### 2.1 v1 最小 Schema

| 通道 | 骨骼/配置 | 为什么 |
|---|---|---|
| **Trajectory** | 采样点：过去 0.33s、现在、未来 0.25s / 0.5s | 轨迹是 MM 的主输入——玩家意图全在这里。四点是社区常见起点（待验证） |
| **Pose: Bone Position** | `foot_l`、`foot_r` | 双脚位置决定步态相位。脚在哪，下一步只能从哪迈 |
| **Pose: Bone Velocity** | `foot_l`、`foot_r` | 区分「脚在支撑」和「脚在摆动」——位置相同速度不同的两帧完全不可互换 |

**刻意不放进 v1 的**：

| 不放 | 原因 |
|---|---|
| 手/脊柱/头骨骼 | locomotion 下它们跟随躯干，信息与脚冗余；加了只会稀释 cost |
| Limb Phase 通道 | 有用但多一个归因维度，v2 再单独评估 |
| root bone 位置 | 特征天然以 root 为参考系，再放 root 位置是零信息 |

### 2.2 骨骼选择与 Step 2 的对应

Step 2 的骨骼角色分类（§9.4）直接复用到这里：

| mp_core 角色 | Schema 用法 |
|---|---|
| `foot`（踝） | **进 Schema**——支撑判定的主信号 |
| `ball`（掌） | v1 不进；若脚踝匹配不够细（大脚掌角色）v2 再加 |
| `toe_tip` | **永不进**——§10.1 实测它支撑相滚动，slide 是踝的 3 倍，作为匹配特征只会引入噪声 |

> 这条对应关系是本项目的独特叙事之一：**数据管线的质量分析直接决定了
> 引擎侧的特征选择**，两边不是孤立的工具。

### 2.3 权重的起点与调法

起点（待引擎验证后回填实际值）：

| 通道 | 初始权重 | 理由 |
|---|---|---|
| Trajectory | 1.0 | 响应性优先——玩家输入是最高优先级 |
| Bone Position | 0.75 | 姿态连续性次之 |
| Bone Velocity | 0.5 | 防抖，但权重过高会让角色「粘」在当前动作上 |

调法（固定实验协议，避免「感觉调参」）：

1. 固定一条测试输入轨迹（§4.2 的「加速→巡航→减速→停」）
2. 每次只动一个权重，±50%
3. 记录：选帧跳变次数、平均 cost、切换延迟帧数
4. 三个数字 + 录屏一起判断，回填本表

## 3. 数据库组织（Step 5 预告，先把决定记下）

| 决定 | 选择 | 原因 |
|---|---|---|
| 每类动作一个 Database 还是全塞一个 | **按姿态族分**：locomotion 一个、idle 一个 | idle 帧混进 locomotion 库会被低速轨迹错误命中（社区常见坑，待验证） |
| 循环 clip 标记 | 在 Database 资产里逐条标 loop | 不标的话末帧→首帧会被当成跳变 |
| 抽帧（pruning） | 用 PoseSearch 自带的采样间隔设置 | §10.4 的结论：这是建库参数，不是片段编辑 |
| 镜像变体 | 作为独立 clip 进库，**不用** UE 的 runtime mirror | 我们的镜像在数据侧已验证（§10.1）；两边同时开会加倍 |

## 4. 验证计划

### 4.1 进引擎前（现在就能做）

- [x] 骨骼角色分类可复用（§2.2 表）
- [ ] 语料覆盖检查：corpus 下齐后，统计速度/方向分布，标出 Schema
      的 Trajectory 采样点覆盖不到的区域（复用 §4.1 的分布工具思路）

### 4.2 进引擎后（Step 5/6）

固定测试输入：**加速 → 巡航 → 急转 → 减速 → 停**。对每个 Schema 变更录：

| 指标 | 工具 | 期望 |
|---|---|---|
| 选帧跳变/秒 | PoseSearch debugger | 越低越好，但不为 0（0 = 不响应） |
| cost 分解 | Rewind Debugger 的 PoseSearch 视图 | 无单通道恒定主导 |
| 输入→动作延迟 | 逐帧数 | ≤ 5 帧（30fps 下 166ms，待验证合理性） |
| 脚滑（视觉） | 眼睛 + 录屏 | 与源 clip 无可见差异 |

### 4.3 待引擎验证的断言清单

本文档所有标了「待验证」的：

1. Trajectory 四采样点（-0.33 / 0 / +0.25 / +0.5s）是否适合本语料的速度范围
2. idle 与 locomotion 分库是否真的必要（先合库测，出问题再分）
3. 初始权重表（§2.3）
4. 5 帧延迟上限是否是合理标准
5. UE 版本目标：**5.4+**（PoseSearch 在 5.4 进生产可用；若装 5.5+ 需重查 API 变化）

## 5. 已知风险

| 风险 | 缓解 |
|---|---|
| Mixamo 骨骼 ≠ UE Mannequin，PoseSearch 对非标准骨骼的支持未知 | 两条路线：A. 语料 retarget 到 UE5 Mannequin 再建库（推荐，用 maya_to_ue 的 skeleton_presets 做映射基础）；B. 直接用 Mixamo 骨骼建 Schema。先试 B，失败成本低 |
| n=30 的语料对 MM 仍偏小 | 预期之内。demo 目标是「管线正确」不是「商业品质」；覆盖缺口本身就是 §4.1 覆盖工具的展示素材 |
| 权重调参无止境 | §2.3 的固定实验协议 + 时间盒（每通道最多 3 轮） |
