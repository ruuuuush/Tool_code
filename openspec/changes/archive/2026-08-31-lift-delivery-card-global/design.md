## Context

`DeliveryCard` 目前在 `ExportPanel.__init__` 里创建，作为导出表单最后一个控件。当初这个归属是对的：导出设置、导出按钮、导出结果同在一页，结果紧跟按钮出现，符合直觉。

`reorder-wizard-steps` 把顺序改成 片段 → 导出设置 → 检查，并把导出按钮放到检查步的导航条上（检查通过才放行，按钮跟着门禁走）。动作移走了，结果没跟上，于是：

- 用户在第③步点导出
- `show_delivery()` 在第②步的面板里渲染
- `main_window.py:1541` 的 `ensureWidgetVisible` 滚动的是第②步的滚动区

那行滚动代码是这次断裂的化石：它写于拆页之前，拆页之后既无效又无害地留着，谁也没察觉。

约束：`DeliveryCard` 自身（三行产物、交接区、推送、降级）已被 spec 与测试覆盖，这次只搬位置，不动它的行为。

## Goals / Non-Goals

**Goals:**
- 导出完成后，结果与后续动作在当前屏幕可见，不论用户停在哪一步。
- 交付结果的归属从"某个步骤的控件"改为"会话级产出"。
- 推送线程的生命周期由新的宿主正确接管。

**Non-Goals:**
- 不改 `DeliveryCard` 的内部结构与行为。
- 不改导出按钮的位置与门禁逻辑。
- 不改推送协议与降级策略。
- 不在未导出时占用界面空间。

## Decisions

### 决策 1：卡片挂到主窗口，位于内容区与导航条之间

层级上它与 `QStackedWidget` 平级，不进任何一页。位置放在内容区下方、导航条上方——视线从上往下走完当前步骤，自然落到结果上；再往下是"上一步/下一步/导出"。

*备选*：搬进检查页。否决——那只是把归属从一个步骤换到另一个步骤，下次再调顺序会重演同样的断裂。而且结果本就不是"检查"的产物。

*备选*：导出后自动跳回第②步。否决——用强制跳页掩盖布局错误，用户还会疑惑"为什么把我弹走了"。

### 决策 2：`show_delivery` 等方法上移到 `MainWindow`

卡片的持有者变了，操作它的方法跟着走：`show_delivery()`、`_copy_to_clipboard()`、`_push_to_ue()`、`_on_push_finished()`、`stop_push()`。

`ExportPanel` 保留 `set_busy()` / `show_errors()` / `set_export_enabled()`——那些是表单自身的状态，与交付产物无关。

### 决策 3：删除 `ensureWidgetVisible` 而不是改它指向新位置

卡片不再嵌在滚动区里，它就在固定位置，无需滚动。留一行"滚到它"的代码只会让人误以为它还可能被藏起来。

### 决策 4：推送线程的回收挂到主窗口的 `closeEvent`

`stop_push()` 原本由 `MainWindow.closeEvent` 调用 `ExportPanel.stop_push()`。方法上移后直接由主窗口自持，链路更短。这条约束本身（在途推送不得活过宿主）已在 `ue-remote-push` spec 中，不因搬家而改变。

## Risks / Trade-offs

- **卡片显示后挤压内容区高度** → 卡片只占内容高度（`SizePolicy.Maximum`），且未导出时隐藏；内容区本就可滚动。
- **测试大面积改动**（原先从 `ExportPanel()` 取卡片） → 改为经主窗口取；这类改动是归属调整的必然成本，一次改完。
- **`ExportPanel` 变"瘦"后职责是否仍清晰** → 它回归纯粹的表单 + 提交状态，反而更内聚。
