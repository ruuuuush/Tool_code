## Context

管线是两个进程：Maya 端写 FBX + manifest，UE 端读 manifest 建资产。`launch_ue_importer.run(manifest_path)` 是后半段的入口，`README` 里写了，但界面上一个字都没有。

`DeliveryCard` 当前只回答「产物落地了吗」，三行 FBX / Manifest / 报告，加一个状态标题。它是导出后用户唯一会盯着看的东西，也正是断层发生的位置——用户看完这三行绿点，合理地认为事情办完了。

已有的抓手：`ExportResult.manifest_path` 就是 UE 侧需要的那个参数，导出成功时它必然有值。也就是说，交接命令所需的全部信息，在显示交付卡片的那一刻已经在手上了。

约束：Maya 端无法验证 UE 那边发生了什么，所以这里只能给指引，不能给状态。指引必须诚实——它说的是「接下来去做什么」，不是「已经做了什么」。

## Goals / Non-Goals

**Goals:**
- 导出完成的那一屏就能看到「还有 UE 这一步」。
- 命令可直接复制运行，不需要用户自己拼路径。
- 只在真正交付完整时出现，不给失败的导出制造虚假的下一步。
- 消除「填了 UE 路径就会自动进 UE」的误解。

**Non-Goals:**
- 不尝试从 Maya 远程驱动 UE（不同进程、不同解释器，做不到也不该做）。
- 不显示 UE 侧的导入结果——Maya 端无从得知。
- 不改 UE 导入逻辑本身。
- 不做 UE 工程路径的探测或校验。

## Decisions

### 决策 1：交接区放进 `DeliveryCard`，不新开面板

导出后用户的视线落点就是交付卡片。「产物在哪」和「接下来干什么」是同一个问题的两半，拆到两个控件里会让第二半再次被忽略——而被忽略正是这次要解决的问题。

### 决策 2：给完整可粘贴的代码块，不是一句话提示

「请在 UE 里运行导入脚本」这种提示等于没说：用户还得去翻 README，找到脚本名，拼出 manifest 路径。既然路径就在手上，直接给出可执行的三行：

```
import sys
sys.path.insert(0, r"<仓库路径>")
import launch_ue_importer
outcome = launch_ue_importer.run(r"<本次 manifest 路径>")
launch_ue_importer.report(outcome)
```

仓库路径从 `__file__` 反推，manifest 路径取 `result.manifest_path`，两个都不需要用户填。

### 决策 3：只在 `is_complete()` 为真时显示

缺 manifest 时给出「去 UE 导入」的指引是有害的——UE 侧根本没有 manifest 可读，用户跑一遍拿到报错，反而更困惑。交付不完整时卡片继续只讲失败原因。

这条同时保证了：能显示交接区，就意味着 `manifest_path` 非空，代码模板里不会出现空路径。

### 决策 4：复制按钮而非可编辑文本框

代码块用只读 `QLabel`（等宽字体、可选中），旁边配复制按钮。用 `QLineEdit` 会诱导用户去编辑，而这段代码不需要改；用可编辑控件还得处理焦点与样式，和刚修完的单元格编辑器是同类麻烦。

### 决策 5：导出设置里的 UE 字段加归属说明，但不加回"说明文字"

spec 有一条「界面不承载说明文字」，禁的是「告诉工具每段动画的帧范围」这类复述控件用途的引导语。这里要表达的是**归属**——这些值去哪、谁来消费，属于状态信息而非操作说明。用分组标题承载（例如把 UE 相关字段归到一个标明去向的小节下），不是在控件旁边贴一行解释。

## Risks / Trade-offs

- **代码块占纵向空间，把产物清单挤下去** → 交接区放在三行产物之后，用户视线自然从上往下走完再看到它；导出页本身有滚动。
- **仓库路径从 `__file__` 反推，在符号链接或网络盘下可能不是用户预期的写法** → 用 `os.path.abspath`；即便路径形式不同，只要可达就能跑通。
- **用户复制后忘了先跑 `check()`** → 指引里附一行注释提示首次使用某个引擎版本时先自检。
- **UE 侧脚本名或签名将来变化，模板会过时** → 模板放在 `strings.py`，与 `launch_ue_importer` 的公开接口一起维护；接口改动本就该同步文案。
